## High-Value Verification (~5 minutes)

### HV.1 -- The diagnosis is visible with ZERO logging setup

Automated tests capture logs via pytest's caplog, which proves nothing about
a real console. Verified at commit time on Windows; re-check on other setups.

- [ ] **Steps** (any OS, fresh interpreter, no logging config):
  ```
  python -c "from dazzle_filekit import find_files; find_files(['C:' + chr(9) + 'emp'], patterns=['*'], recursive=False)"
  ```
- [ ] **Expected:** TWO warnings on stderr -- the plain miss, then
  `did you mean 'C:\\temp'? (use a raw string r'...' or double the backslashes)`.
- [ ] **Why:** the design is warn-only; if the warning is invisible in default
  config, the feature does not exist. (filekit attaches a console handler by
  default -- if that ever changes to a NullHandler, this item catches it.)
- [ ] **Note the repr is doing work:** `'C:\\temp'` shows a doubled backslash,
  which is exactly what the user should type in source. Do not "fix" it.

### HV.2 -- The drive-walk regression, timed

- [ ] **Steps:** `python -c "from dazzle_filekit import find_files; find_files('C:\\')"` 
- [ ] **Expected:** instant `TypeError ... Did you mean ['C:\\']?`. If this
  takes more than a heartbeat, the guard is gone and it is enumerating the
  drive -- kill it and report.

### HV.3 -- All five entry points guard, including bare Path

- [ ] **Steps:** call each of `find_files`, `find_regex_files`,
  `calculate_total_size`, `copy_files_with_path`, `move_files_with_path`
  with a bare string AND a bare `Path(...)` in the collection slot.
- [ ] **Expected:** every combination raises `TypeError` naming the
  bracketed form. A bare `Path` must NOT say "'WindowsPath' object is not
  iterable".

### HV.4 -- Recovery is literal-first and opt-in

- [ ] **Steps:** in a scratch dir create `temp/`, then:
  ```
  python -c "import sys; from dazzle_filekit import recover_unescaped_path as r; print(r(sys.argv[1] + chr(9) + 'emp'))" <scratch-dir-path-without-trailing-sep>
  ```
- [ ] **Expected:** `('<scratch>\\temp', True)`. Then confirm an ordinary
  existing path returns `(path, False)` untouched, and that NO filekit
  function applies recovery automatically -- only the warning fires.

### HV.5 -- Downstream blast radius (verified at commit time)

- [ ] Grep of all seven dependent repos (csb, dazzlecmd, dazzlecmd-lib,
  preservelib, dazzlesum, dazzlelink, UNCtools) found **zero** bare-string
  calls to the five guarded functions. Re-run on new consumers before
  raising the floor:
  ```
  grep -rn --include="*.py" -E "(find_files|find_regex_files|calculate_total_size|copy_files_with_path|move_files_with_path)\s*\(\s*['\"]" <repo>
  ```

## What the automated tests DON'T cover

- Console rendering of the warnings outside pytest (HV.1).
- Wall-clock character of the drive-walk regression (HV.2 -- the test asserts
  the raise, not the "instant").
- POSIX: control characters ARE legal in POSIX filenames; literal-first means
  such a file always wins over recovery. Asserted in tests only via mocks --
  never executed on a real POSIX filesystem.
- Whether the TypeError wording actually reads as "add brackets" to someone
  who has not seen this checklist.
