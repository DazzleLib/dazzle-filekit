## What this is

v0.3.3 is claimed **additive-only**: a new `pathenv` module (pure string logic) and one internal regex single-sourcing in `utils/compat.py`. The automated suite proves the string logic; this short checklist covers the two things only a real machine shows: the R1-touched `resolve_cross_platform_path` against a live filesystem, and real downstream consumers importing the new surface. It is deliberately small -- pathenv does no I/O, so most mocks-can't-see-it categories do not apply.

## Section 1: Declared-platform semantics spot-checks (~3 min)

### 1.1 Windows value parsed identically regardless of host

- [ ] **Steps:** on any box: `python -c "from dazzle_filekit.pathenv import split_path_value; print(split_path_value(r'C:\\a;C:\\b', platform='windows'))"`
- [ ] **Expected:** `['C:\\a', 'C:\\b']` -- split on `;` even on a POSIX host (run on both if available).

### 1.2 `%VAR%` expansion works on POSIX hosts too

- [ ] **Steps** (POSIX box if available): set an env var and check `normalize_path_entry('%MYVAR%/bin', platform='windows')` expands it.
- [ ] **Expected:** expansion happens (ntpath-based), backslash form, casefolded.

### 1.3 Undefined `%VAR%` stays literal

- [ ] **Steps:** `python -c "from dazzle_filekit.pathenv import normalize_path_entry; print(normalize_path_entry(r'%NO_SUCH_VAR_XYZ%\\bin', platform='windows'))"`
- [ ] **Expected:** the literal `%no_such_var_xyz%\bin` (unexpanded, casefolded) -- same leave-it-literal behavior filekit's other expanders document.
